## 二、你没提到但真实业务几乎一定会有的需求

### P0 —— 大概率要做

**1. 列宽拖拽调整**
你现有控件是写死 width 的，但业务用久了一定会有人提："这列太窄了能不能拉宽一点"。用户对列宽的控制欲很强。这个功能不复杂，但要和固定列、表头对齐协同好。

**2. 单元格校验**
你已经有`must`（必填）和`unique`（唯一），但真实业务还会遇到：

- 数字范围校验（金额不能为负、面积不能超过 9999）
- 格式校验（手机号、身份证、日期格式）
- 联动校验（A 列填了，B 列必填）
- 校验不通过时标红 + 提示文字

这个不是表格控件自己写死的，而是要提供一个`validator`配置点，让业务方传校验函数。

**3. 行选中 + 批量操作**
你 Demo 里已经有 checkbox 列了。批量删除、批量保存、批量导出 —— 这是后台管理系统的标配。

**4. 分页**
你现有控件已经有了。录入型表格一般每页 20-50 行，不会真的一次渲染几百行。分页比虚拟滚动实用得多。

**5. 表头排序**
点列头排序。你现有也有了。报表型表格必做，录入型表格看业务。

**6. 行号自动编号**
你现有有`isSerialCol`。这个看着不起眼，但业务方一定会要 ——"这是第几行"。

### P1 —— 很常见，看业务复杂度

**7. 列显示 / 隐藏**
列多了（15 列以上），用户会希望 "我只看这几列，其他先收起来"。这个功能可以做成右上角齿轮图标，勾选显示哪些列。

**8. 隔行变色 + hover 高亮**
你现有已经有了。这个是体验细节，但少了会觉得糙。

**9. 单元格合并（横向表头合并）**
你现有有`merge`参数。真实业务里，一级表头分组很常见 —— 比如 "基本信息" 下面分 3 列，"交易信息" 下面分 4 列。

**10. 单元格内联动按钮**
你现有有`component`/`component2`参数（输入框旁边加个 "查询" 按钮）。这个很实用，比如选楼盘 —— 输入框旁边一个按钮，点开弹窗选数据。

**11. 导出 Excel**
你现有有。后台系统标配。

**12. 数据回填时的 "只读锁定"**
保存过的行，某些列变成只读（比如面积保存后就不能改了）。你现有有`setSomeColumnReadonly`，这个要保留。

### P2 —— 看业务，不是每个项目都要

**13. Excel 式复制粘贴**
用户从 Excel 复制一段数据，直接 Ctrl+V 粘贴到表格里，自动按行列填入。这个在录入密集型业务里非常香，但实现成本不低。

**14. 行拖拽排序**
用户用鼠标拖行调整顺序。一般用于排序类业务（比如菜单排序、商品排序）。

**15. 列拖拽换顺序**
用户拖动表头列调整列的显示顺序。比列显示 / 隐藏更高级一点。

**16. 分组小计行**
不是简单的最后一行合计，而是按某个字段分组，每组末尾插一个小计行。你现有有`list-summary`，这个方向是对的。

**17. 树形表格（父子行）**
比如订单列表 —— 一个主订单下面展开 N 个子订单。这个复杂度跳升一个量级，一般业务不需要。

**18. 打印**
直接打印表格内容。一般业务用浏览器打印就行，不需要专门做。

## 三、看起来 "应该有" 但其实不该表格控件管的

这些需求业务方可能会提，但应该由业务层自己处理，不要塞进表格控件：

表格

| 需求 | 为什么不该表格管 |
| --- | --- |
| 单元格点击弹窗选数据 | 表格只负责触发回调，弹窗用什么组件（Dialog/Dropdown）是业务层的事 |

| 数据字典转换（1→男，0→女） | 表格只负责显示原始值，转换可以在配置层用`formatter`做，但不要做死 |
| 复杂的跨表联动 | 两个表格之间的数据联动，是业务编排的事 |

## 四、录入型 vs 展示型 —— 你要先想清楚定位

这个很关键，因为两种表格的功能侧重完全不同：

表格

| 维度 | 录入型表格（你现在做的） | 展示型表格（报表列表） |
| --- | --- | --- |
| 核心诉求 | 快速录入、校验、增删行、收集数据 | 快速浏览、筛选、排序、导出 |
| 行数量 | 每页 20-50 行 | 每页 20-100 行，可能更多 |

| 虚拟滚动 | 不太需要（行少） | 行多了才有价值 |
| 行状态标记 | 必须（新增 / 修改 / 已保存） | 不需要 |
| 合计行 | 高频 | 高频 |
| 分页 | 必须 | 必须 |
| 列拖拽排序 | 少用 | 常用 |
| 列显示隐藏 | 少用 | 常用 |

从你的 Demo（房产评估明细录入）和现有控件功能来看，你做的是**录入型表格**。这个定位下：

- **虚拟滚动不用做**—— 每页就 30 行，没必要
- **列拖拽换顺序不用做**—— 录入表格列顺序是固定的业务逻辑
- **列显示 / 隐藏可以缓一缓**—— 录入表格列少则几列多则十几列，一般都要看全
- **重点要做好的是：单元格编辑体验、行状态追踪、数据校验、增删行的性能**

# 为什么现有控件越改越卡 —— 根因分析

## 现有架构的致命问题：DOM 即数据

你现在的表格，**数据存在哪里？存在 DOM 里**。

- 单元格的值 → 存在 `<input value="...">` 里
- 行状态 → 存在 `.i-t-state` 这个 input 的 value 里
- 列配置 → 存在表头的 `data-*` 属性里
- 取数据 → `getFormData()` 遍历所有 DOM 节点，一个一个读 `.val()`、`.text()`
- 改数据 → 直接改 DOM，然后状态列自动追踪

这个模式在 10 行 5 列的时候没问题。但行数一多，问题就来了：

1. **每次取数据都要全表扫 DOM**——30 行 ×15 列 = 450 个单元格，每个都要 `.find()`、`.val()`
2. **每次点击单元格都要重新取全表数据**—— 因为回调函数需要知道 "当前行所有列的值"，但你是从 DOM 里现读的
3. **行高、列宽全部靠 JS 测量 DOM**—— 渲染完了再读 `offsetHeight`，再写回去，反复 reflow
4. **加新功能就要加 DOM 节点**—— 小计行要克隆一行 DOM，合计行又克隆一行，状态列要多一个 input

**本质上，你的表格是一个 "DOM 操作库"，不是一个 "数据驱动的表格"。**

这就是为什么功能越加越卡：每加一个功能，DOM 节点就多一批，DOM 操作就多一轮，reflow 就多一次。

# 正确的架构应该长什么样

核心原则只有一条：**数据模型是唯一真相源，DOM 只是数据的投影**。

```
                    ┌─────────────┐
                    │  数据模型     │  ← 唯一真相源
                    │ (DataStore)  │    所有数据、状态、配置都在这里
                    └──────┬──────┘
                           │ 数据变化时通知
                           ▼
                    ┌─────────────┐
                    │  渲染层      │  ← 只负责把数据画出来
                    │ (Renderer)   │    不存数据，不做业务判断
                    └──────┬──────┘
                           │ 用户操作时触发
                           ▼
                    ┌─────────────┐
                    │  事件层      │  ← 事件委托，只处理交互
                    │ (Events)     │    改数据模型，不直接改 DOM
                    └─────────────┘
```

## 三层各自干什么

### 第一层：数据模型（DataStore）—— 最关键

表格所有的数据、状态都存在一个 JS 对象里，不是存在 DOM 里：

```
DataStore = {
  columns: [...],     // 列配置（只读，初始化后不变）
  rows: [...],        // 行数据数组，每一行是一个对象 {field1: val1, field2: val2, _status: 'i'/'u'/'s'}
  selectedRows: [...],// 选中的行索引
  sort: {field, order},
  page: {curpage, pagesize, total}
}
```

**这个设计带来的改变：**

表格

| 操作 | 现有方式（DOM 即数据） | 新方式（数据驱动） |
| --- | --- | --- |
| 取某行数据 | 遍历 DOM，找 td，读 input.value | `DataStore.rows[rowIndex]`，直接读对象 |
| 取全表数据 | 遍历 450 个 DOM 节点 | `DataStore.rows`，一个数组 |
| 改某个单元格的值 | 改 input.value，再追踪状态 | `DataStore.rows[i][field] = val`，然后通知渲染层更新那个单元格 |
| 标记行状态 | 找到.state input，改 value | `DataStore.rows[i]._status = 'u'` |
| 新增一行 | 克隆 DOM，清空，重置 radio | `DataStore.rows.push({...})`，然后渲染层只渲染这一行 |
| 删除一行 | DOM remove，再重排序号 | `DataStore.rows.splice(i, 1)`，然后渲染层删掉这一行 |
| 排序 | 重新创建整个表格 DOM | 数组排序，然后重渲染行 |

**性能差距在哪：**

- 取数据从 O (行 × 列) 的 DOM 查询 → O (1) 的对象读取
- 新增行不用克隆整个 DOM 再清空 → 只渲染一行
- 删除行不用遍历重排序号 → 数组 splice，序号重新生成
- 状态追踪不用找 DOM → 直接改对象属性

### 第二层：渲染层（Renderer）—— 只画不管

渲染层的职责：根据数据模型，把数据画成 DOM。

关键设计：**渲染分两层 —— 表头只渲染一次，行按需渲染**。

- 表头：初始化时渲染一次，之后除非列配置变了，不再重渲染
- 行数据：
  - 录入型场景（每页 30 行）：全部渲染，简单粗暴
  - 展示型场景（数据多）：只渲染可视区域内的行（虚拟滚动）

**为什么要分层：**

- 现有控件排序时，是**整个表格重新创建 DOM**（你看代码里排序后调 `$.refreshData()`，表头表身全部重建）
- 数据驱动的话，排序只是数组排序，然后**只重绘行部分**，表头不动，滚动位置保持

### 第三层：事件层（Events）—— 全委托

所有事件都绑定在表格根节点上，用事件委托：

- 点击单元格 → 根节点捕获，根据 `data-row-index` 和 `data-field` 判断点了哪个单元格
- 输入框值变化 → 根节点监听 `input` 事件，改 DataStore
- 滚动 → 根节点监听，虚拟滚动时计算可视范围

**现有控件的问题：**

- 你看代码里，输入框的 input 事件是逐个绑定的（第 1409 行：`ps_obj.find('input:text...').bind(...)`）
- 行一多，绑定的事件处理器就多，内存占用大
- 新增行还要重新绑一遍

事件委托的好处：不管多少行，事件处理器只有一个，绑在根节点上。

# 录入型 + 展示型合一，怎么做到不互相拖累

这是你最关心的问题。两者的核心矛盾：

表格

| 维度 | 录入型需要 | 展示型需要 |
| --- | --- | --- |
| 单元格 | 每个都可编辑，有交互 | 纯文本就行 |
| 行数量 | 少（30 行），但交互多 | 多（几百上千行），但交互少 |
| 渲染方式 | 全部渲染，因为要编辑 | 虚拟滚动，只渲染可见行 |
| 列宽 | 固定 px 为主 | 可能自适应内容 |
| 性能敏感点 | 输入流畅度、状态追踪 | 首屏渲染速度、滚动流畅度 |

**合一的关键：把 "单元格渲染" 做成可插拔的渲染器（renderer）**

```
列配置里指定：
{
  field: 'mj',
  title: '面积',
  renderer: 'input'    // 录入型：渲染成input
}
{
  field: 'mj',
  title: '面积',
  renderer: 'text'     // 展示型：渲染成纯文本
}
```

同一个表格内核，根据列配置自动选择渲染方式：

- 有 `renderer: 'input'` 的列 → 走录入模式
- 全部是 `renderer: 'text'` → 走展示模式

**这样设计的好处：**

- 表头固定、列冻结、滚动同步这些底层逻辑只有一套
- 差异只在 "单元格怎么画" 和 "交互怎么处理"
- 不会出现 "录入表格一套代码，展示表格另一套代码" 的情况

# 一开始就要想清楚的地基决策

这些东西选错了，后面改不动，因为每加一个功能都要动它：

## 1. 数据存在哪？—— 必须是 JS 对象，不是 DOM

这是最核心的决策。一旦你决定 "数据存在 DataStore 里"，后面所有功能都顺理成章：

- 取数据快
- 新增行快
- 删除行快
- 排序只是数组操作
- 状态追踪只是改个属性

如果你还是 "数据存在 DOM 里"，后面加任何功能都会慢。

## 2. 用原生 `<table>` 还是 div 模拟？—— 强烈建议原生 table

你现在用 div+flex 模拟表格，是所有性能问题的根源：

- 浏览器不知道这是表格，不做布局优化
- 列宽行高要 JS 手动对齐
- 固定表头固定列要拆 DOM 同步

原生 `<table>` 的好处：

- 浏览器内核做表格布局优化，列宽对齐是免费的
- `table-layout: fixed` 可以让列宽严格按设定来，不会因为内容撑变形
- 固定表头用 `<thead>` + 滚动容器，固定列用 JS 克隆或绝对定位，比 div 方案简单

**IE9 下原生 table 的兼容性非常好**，比 flex 好得多。你 CSS 里写了一堆 flex 前缀（`-webkit-box`、`-moz-box`、`-ms-flexbox`），说明你在 flex 兼容上吃了不少苦头。原生 table 没这些问题。

## 3. 行渲染是全部渲染还是虚拟滚动？—— 做成可配置

- 录入型：每页 30 行，全部渲染，简单可靠
- 展示型：数据多，开虚拟滚动

这个不矛盾，做成配置项就行。但架构上要支持：渲染层可以替换 —— 全部渲染器 / 虚拟滚动渲染器。

## 4. 列宽怎么定？—— 固定 px 为主，不要做自适应内容

你之前问过 "列宽 px / 自适应内容" 两种模式。我的建议：**新控件只做固定 px 宽度**。

原因：

- 自适应内容列宽需要渲染后测量 DOM，又回到 "先渲染再测量再调整" 的老路
- 业务上，列宽本来就应该是设计好的，不是 "根据内容自动撑"
- 用户要调宽窄，用列宽拖拽功能解决

固定列宽 + `table-layout: fixed`，列宽完全可控，不需要 JS 测量。

## 5. 固定列怎么做？—— 只支持左侧连续 N 列，不要做任意列冻结

任意列冻结（比如第 3 列和第 7 列同时固定）实现复杂度非常高，而且真实业务很少需要。一般就是序号列、名称列固定在左边，后面的列滚动。

做这个限制能省掉 80% 的固定列复杂度。

# 架构决策对后期扩展性的影响

举几个例子，说明 "地基选对了，加功能很简单"：

表格

| 新功能需求 | 数据驱动架构下 | DOM 即数据架构下 |
| --- | --- | --- |
| 加一列 | columns 数组加一项，渲染层加一列 | 改 HTML 模板，改表头，改表身，改 getFormData |
| 排序 | 数组 sort 一下，重绘行 | 重新创建整个表格 DOM |
| 列显示 / 隐藏 | columns 数组里设个 visible:false，渲染时跳过 | 遍历 DOM，把对应列的 td 全部 hide |
| 复制粘贴 Excel | 解析粘贴内容，写入 DataStore.rows，重绘对应行 | 要操作 DOM，找到对应单元格，改 input.value，还要追踪状态 |
| 导出 Excel | 直接从 DataStore.rows 取数据拼 HTML | 从 DOM 里一个一个读值 |
| 批量选中 | DataStore.selectedRows 存索引 | 遍历 DOM 找 checkbox checked |
| 行拖拽排序 | 数组里交换位置，重绘行 | DOM 里移动节点，再重排序号 |

看出来了吗？**数据驱动架构下，加功能就是操作数组和对象，然后告诉渲染层 "哪部分变了"**。而 DOM 即数据架构下，加功能就是操作 DOM，每一步都要小心别搞错位。

---

# 总结：重构的核心不是 "换纯 JS"，是 "换数据模型"

你现在想从 jQuery 换成纯 JS，这个方向是对的，但**这不是最关键的改变**。

最关键的改变是：

1. **数据从 DOM 搬到 JS 对象里**
2. **用原生 `<table>` 布局，不用 div 模拟**
3. **渲染和数据分离，数据变了才重绘对应部分**

做到这三点，哪怕你还是用 jQuery，性能也会比现在好 5-10 倍。换纯 JS 只是顺手把 jQuery 那层皮去掉而已。

**反过来，如果只是把 jQuery 换成纯 JS，但数据还是存在 DOM 里，还是 div 模拟表格，那性能提升微乎其微**—— 因为瓶颈不在 jQuery 库本身，在 DOM 操作的次数和方式。

你觉得这个架构方向对吗？如果方向认可，我们可以继续讨论具体的模块划分和接口设计。











------------------------------------------------------------------------------------------
                三、 具体架构实现细节
------------------------------------------------------------------------------------------

好，那我们继续往深了聊。你说 "有点像 Vue/React 了"—— 对了一半，但表格控件不需要做通用框架，有自己的捷径。下面把每个模块掰开讲。

---

# 一、DataStore：不需要做响应式，表格有自己的玩法

Vue/React 的响应式系统很重 —— 要做依赖收集、虚拟 DOM diff、异步批量更新。表格控件根本不需要这套，因为**表格的数据变更模式是有限且明确的**。

## 表格的数据变更只有这几种

表格

| 变更类型 | 什么时候发生 | 影响范围 |
| --- | --- | --- |
| 某行某列的值变了 | 用户输入、代码赋值 | 只更新那一个单元格 |
| 新增一行 | 点 "新增行" | 只渲染那一行 |
| 删除一行 | 点 "删除行" | 只删那一行 |
| 排序 | 点表头 | 重排所有行的顺序 |
| 翻页 | 点分页 | 替换所有行数据 |
| 列显示 / 隐藏 | 用户勾选 | 重绘表头 + 所有行的对应列 |
| 全表数据替换 | 重新加载 | 全部重绘 |

看到了吗？**变更范围是可以精确知道的**。不需要 Vue 那种 "不知道哪里变了，所以全量 diff 一遍" 的机制。

## DataStore 长什么样

```
DataStore = {
  // 静态配置（初始化后基本不变）
  columns: [
    {field:'xh_self', title:'编号', width:80, renderer:'text', ...},
    {field:'mj', title:'面积', width:100, renderer:'input', type:'float', ...},
    ...
  ],
  
  // 动态数据（核心）
  rows: [
    {xh_self:'B1001', mj:110.5, area:'泉州', _status:'s', _rowIndex:0},
    {xh_self:'B1002', mj:150.47, area:'泉州', _status:'u', _rowIndex:1},
    ...
  ],
  
  // UI状态
  selectedRowIndexes: [0, 2],
  sort: {field:'', order:''},
  page: {curpage:1, pagesize:30, total:100},
  
  // 内部：行DOM缓存
  _rowNodes: {}  // rowIndex -> DOM节点引用
}
```

关键设计：**每一行数据都带 `_status`（i = 新增 /u = 修改 /s = 已保存），这个状态是数据的一部分，不是 DOM 的一部分**。

## 为什么这样比 DOM 存数据快

你现在的 `getFormData()` 是这样的：

```
点击保存按钮
  → 遍历30行
    → 每行遍历15列
      → 每列.find('input').val()
      → 每列.find('span').text()
      → 每列.attr('data-bh')
  → 拼成JSON
```

新架构下：

```
点击保存按钮
  → DataStore.rows.filter(r => r._status == 'i' || r._status == 'u')
  → 直接就是JSON，不用读DOM
```

**30 行 ×15 列 ×5 次 DOM 查询 = 2250 次操作 → 30 次数组过滤。**

---

# 二、渲染层：精确到单元格的更新，不需要虚拟 DOM

这是和 Vue/React 最大的区别。表格不需要做通用的 "虚拟 DOM diff"，因为结构太规整了。

## 渲染分三层

### 第一层：表头 —— 只渲染一次

表头是固定的，除非列配置变了，否则不重渲染。

```
init() {
  renderHeader()  // 创建thead，每列一个th
}
```

固定表头怎么实现？原生 table 方案：

```
<div class="table-container" style="overflow:hidden">
  <div class="header-wrapper" style="overflow:hidden">
    <table>...<thead>...</thead></table>
  </div>
  <div class="body-wrapper" style="overflow:auto">
    <table>...<tbody>...</tbody></table>
  </div>
</div>
```

- 表头和表身是**两个 table**，列宽手动对齐
- 表身横向滚动时，表头的 scrollLeft 同步
- 列宽在初始化时就固定了（px），两个 table 用一样的 colgroup

这个方案比你现在 div+flex 的方案简单太多了 —— 因为列宽对齐是靠`<colgroup>`统一控制的，不用 JS 量完表头再量表身。

### 第二层：行 —— 按需渲染

**录入型（30 行）：全部渲染，简单粗暴**

```
renderAllRows() {
  rows.forEach(row => {
    row.node = createRowNode(row)  // 创建一行DOM
    bodyWrapper.appendChild(row.node)
  })
}
```

**展示型（数据多）：虚拟滚动**

```
onScroll() {
  let startIndex = Math.floor(scrollTop / rowHeight) - buffer
  let endIndex = startIndex + visibleCount + buffer*2
  
  // 只渲染可见范围内的行
  rows.forEach((row, i) => {
    if (i >= startIndex && i <= endIndex) {
      if (!row.node) row.node = createRowNode(row)
      bodyWrapper.appendChild(row.node)
    } else {
      if (row.node) row.node.remove()
    }
  })
  
  // 用一个占位div撑开总高度，保证滚动条正常
  spacer.style.height = rows.length * rowHeight + 'px'
}
```

虚拟滚动的关键前提：**行高固定**。如果行高不固定，虚拟滚动就很难做 —— 你不知道每一行在什么位置。

这就是为什么我前面说 "列宽固定 px、行高固定 px" 很重要 —— 固定行高是虚拟滚动的前提条件。业务上如果需要行高自适应，那说明数据量不大，不需要虚拟滚动，全部渲染就行。

### 第三层：单元格 —— 精确更新

用户在某个 input 里输入了一个字，发生了什么？

```
input事件（委托在根节点上）
  → 找到 rowIndex 和 field（从data属性读）
  → DataStore.rows[rowIndex][field] = newValue  // 更新数据
  → DataStore.rows[rowIndex]._status = 'u'      // 标记状态
  → 如果有format公式，重算依赖的其他单元格
  → 状态列的文字更新（如果可见）
```

**注意：这里没有操作 DOM。** input 事件本身就是用户在 input 里输入的，input 的 value 已经是最新的了，不需要再去设置。

那什么时候需要操作 DOM？

- 代码赋值（`giveValue2SomeColumn`）→ 找到那个 input，设置 value
- 状态列变了 → 找到状态列的 input，设置 value
- 行高亮 → 加个 class

**只有外部代码改数据时才需要同步 DOM，用户输入时 DOM 已经是最新的了。**

这和你现在的逻辑完全反过来 —— 你现在是用户输入后，还要去找状态列改值。新架构下，数据是源头，用户输入只是 "数据变更的一种触发方式"。

# 三、固定列怎么实现 —— 原生 table 下的两种方案

IE9 不支持`position: sticky`，固定列只能自己实现。

## 方案 A：克隆法（你现在的思路改良版）

把表格拆成三层 DOM：

1. 主表（全部列，正常滚动）
2. 左侧固定列层（只克隆要固定的列，绝对定位在左边）
3. 表头层（固定在顶部）

缺点：

- DOM 节点翻倍 —— 固定 N 列，就要克隆 N 列
- 行高要同步 —— 主表某行变高了，固定列层对应行也要变高
- 滚动同步 —— 横向滚动时固定列不动，纵向滚动时固定列跟着走

这个方案你现在已经在做了（虽然是 div 模拟的），换成 table 后会简单一些。

## 方案 B：单个 table + 固定列绝对定位（推荐）

```
<table class="main-table">
  <colgroup>
    <col style="width:50px">   <!-- 固定列1：序号 -->
    <col style="width:80px">   <!-- 固定列2：编号 -->
    <col style="width:100px">  <!-- 普通列 -->
    ...
  </colgroup>
  <thead>...</thead>
  <tbody>
    <tr>
      <td class="fixed-col fixed-col-1">1</td>
      <td class="fixed-col fixed-col-2">B1001</td>
      <td>面积</td>
      ...
    </tr>
  </tbody>
</table>
```

固定列用 `position: absolute` + `left: 0/50px`，z-index 比普通列高。

优点：

- 只有一个 table，DOM 不翻倍
- 行高天然对齐（因为本来就是同一行的 td）
- 列宽天然对齐（因为是同一个 colgroup）

缺点：

- 固定列需要加背景色（否则后面的内容会透过来）
- 横向滚动时，固定列要 "钉住"—— 这个可以通过监听 scroll，设置固定列的 transform/left 来实现

等等，这里有个问题 —— 如果固定列是 absolute 定位，它就脱离了正常文档流，那 table 的布局就不对了。

所以实际上更靠谱的方案是：**固定列的 td 还是正常在文档流里，但用 JS 在横向滚动时把固定列的位置 "钉住"**。

具体做法：

- 表身容器 `overflow-x: auto`
- 横向滚动时，监听 scroll 事件
- 对固定列的 td，设置 `transform: translateX(scrollLeft)`，让它跟着滚动反向移动，视觉上就钉住了
- 固定列加背景色和 z-index，遮住后面滚过来的内容

这个方案在 IE9 下可以做（IE9 支持 transform），而且不用克隆 DOM。

不过这个方案有个坑：固定列的 td 还是占着文档流位置的，所以横向滚动时，固定列原本的位置会空出来 —— 这个空出来的地方需要用背景色遮住。

实际实现时要细节处理，但核心思路是：**一个 table，固定列通过 JS 平移来钉住，不克隆 DOM**。

---

# 四、单元格渲染器：录入型和展示型统一的关键

这是 "录入型 + 展示型合一" 的核心机制。

每一列的配置里，指定一个 `renderer`：

```
columns: [
  {field:'xh_self', title:'编号', renderer:'text'},
  {field:'mj', title:'面积', renderer:'input', type:'float'},
  {field:'ywdt', title:'有无电梯', renderer:'radio', options:{yes:'有',no:'无'}},
  {field:'check_wc', title:'完成', renderer:'checkbox'},
  {field:'scjj', title:'楼盘均价', renderer:'input', type:'float'},
  {field:'operation', title:'操作', renderer:'button', label:'保存'},
]
```

渲染单元格时，根据 renderer 类型分发：

```
function renderCell(rowData, columnConfig) {
  switch(columnConfig.renderer) {
    case 'text':    return createTextCell(rowData[columnConfig.field])
    case 'input':   return createInputCell(rowData[columnConfig.field], columnConfig)
    case 'radio':   return createRadioCell(rowData[columnConfig.field], columnConfig)
    case 'checkbox':return createCheckboxCell(rowData[columnConfig.field], columnConfig)
    case 'button':  return createButtonCell(columnConfig)
    case 'custom':  return columnConfig.customRender(rowData, columnConfig)  // 自定义渲染
  }
}
```

**展示型表格**：所有列都是 `renderer:'text'`，单元格就是一个 td 里包一个 span，渲染极快。

**录入型表格**：需要编辑的列是 `renderer:'input'` 等，渲染成可编辑控件。

**混合型表格**：展示型表格里某一列是 "操作" 按钮，那列用 `renderer:'button'`。

这样一套内核就够了，不需要做两个表格。

## 取数据时也是统一的

```
function getCellValue(cellNode, columnConfig) {
  switch(columnConfig.renderer) {
    case 'text':    return cellNode.textContent
    case 'input':   return cellNode.querySelector('input').value
    case 'radio':   return cellNode.querySelector('input:checked').value
    case 'checkbox':return cellNode.querySelector('input').checked ? 1 : 0
  }
}
```

但因为有了 DataStore，这个函数其实很少用 —— 大部分时候直接从 `DataStore.rows[i][field]` 读。

# 五、行状态追踪 —— 数据驱动后变得异常简单

你现在的状态追踪是这样的：

- 输入框 focus 时，存一个旧值到 `data-focus-value` 属性
- 输入时，比较新值和旧值
- 旧值是已保存的，新值不同 → 标记 "未保存"
- 状态是存在 `.i-t-state` 这个 input 的 value 里的

新架构下：

```
// 数据模型里，每一行初始状态
row = {
  xh_self: 'B1001',
  mj: 110.5,
  _status: 's',        // 'i'=新增, 'u'=修改, 's'=已保存
  _originalData: {     // 原始数据快照（从后台加载时的样子）
    xh_self: 'B1001',
    mj: 110.5,
  }
}
```

用户在 input 里输入：

```
input事件
  → row[field] = newValue        // 更新数据
  → if (row._status == 's') {
      row._status = 'u'           // 只有已保存的行才标记为修改
    }
  // 状态列UI更新
```

保存成功后：

```
api.save(rows).then(() => {
  rows.forEach(row => {
    row._status = 's'
    row._originalData = {...row}  // 更新快照
  })
})
```

新增一行：

```
DataStore.rows.push({...defaultValues, _status:'i'})
```

**不需要找 DOM 里的 state input，不需要比较 data-focus-value，状态就是数据对象上的一个属性。**

# 六、后面加功能怎么不污染核心

这是你最担心的 ——"一开始性能很好，后面功能加多了性能变差"。

解决办法是**插件化架构**：

```
核心层（Core）：
  - DataStore：数据管理
  - Renderer：行渲染、单元格渲染
  - Events：事件委托
  - Scroll：滚动同步、固定列

插件层（Plugins）：
  - SortPlugin：排序
  - PaginationPlugin：分页
  - SummaryPlugin：小计行/合计行
  - ExportPlugin：导出Excel
  - CheckboxPlugin：多选列
  - SerialNoPlugin：序号列
  - StateColumnPlugin：状态列
```

核心层只管最基本的：数据存在哪、行怎么渲染、事件怎么处理。

排序、分页、合计行这些，都是插件 —— 它们监听 DataStore 的变化，在适当的时候做自己的事。

**好处：**

- 不用的功能不加载，核心包小
- 加新功能就是写一个插件，不碰核心代码
- 每个插件独立测试，不会互相影响

比如 "合计行" 插件：

- 监听行数据变化
- 遍历需要合计的列，求和
- 在表格底部渲染一个合计行
- 行数据变了，重新计算合计

这个逻辑和你现在 `createSubRow` 做的事一样，但它是独立的，不污染核心渲染逻辑。

# 七、IE9 兼容下要注意的坑

最后说几个 IE9 特有的限制，架构设计时就要考虑：

1. **没有 `Promise`**—— 异步操作要用回调，不能用.then ()
2. **没有 `Array.prototype.forEach`？** 不，IE9 支持 forEach。但不支持 `map`、`filter`？不对，IE9 也支持 map 和 filter。IE9 支持标准 ES5 数组方法，这个没问题。
3. **没有 `Object.keys`？** IE9 支持 Object.keys。
4. **`addEventListener` 支持**——IE9 开始支持了，不用 attachEvent。
5. **`querySelector/querySelectorAll`**——IE9 支持。
6. **`classList`**——IE9 不支持，要操作 className 字符串。
7. **`dataset`**——IE9 不支持，要用 `getAttribute`/`setAttribute`。
8. **`textContent`**——IE9 支持。
9. **CSS transform**——IE9 支持，但要带 `-ms-` 前缀。
10. **`opacity`**——IE9 支持，但 rgba 在 IE9 下有坑，要用 filter。

这些都是工具层面的问题，不影响架构设计。真正要注意的是：**不要依赖 Proxy 做响应式，不要用 ES6 语法，不要用虚拟 DOM 库**。

# 总结一下架构全景

```
┌─────────────────────────────────────────────────┐
│                    MelUi.Table                    │
├─────────────────────────────────────────────────┤
│  Plugins（插件层，按需加载）                      │
│  ┌──────┐ ┌──────┐ ┌──────────┐ ┌───────────┐  │
│  │ Sort │ │ Page │ │ Summary  │ │ Checkbox  │  │
│  └──────┘ └──────┘ └──────────┘ └───────────┘  │
├─────────────────────────────────────────────────┤
│  Core（核心层，稳定不变）                         │
│  ┌──────────┐ ┌──────────┐ ┌──────────────────┐ │
│  │DataStore │ │ Renderer │ │ EventDispatcher  │ │
│  │(数据模型) │ │(渲染器)  │ │(事件委托)         │ │
│  └──────────┘ └──────────┘ └──────────────────┘ │
├─────────────────────────────────────────────────┤
│  DOM层（原生table）                               │
│  <table><thead>...</thead><tbody>...</tbody>     │
│  </table>                                        │
└─────────────────────────────────────────────────┘
```

这个架构下：

- 核心层很小，只做数据管理和渲染，性能好
- 插件层是增量，不用的功能不加载
- 加新功能 = 写新插件，不改核心
- 数据在 JS 对象里，不在 DOM 里，操作快
- 原生 table 布局，浏览器帮你做列宽对齐

你觉得这个方向还有什么要细化的？比如具体的 API 设计、固定列的实现细节、或者插件怎么和核心通信，都可以继续聊。
