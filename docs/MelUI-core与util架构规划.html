melui.core · melui.util · 架构决议稿 v2

core 与 util 怎么分、怎么导、怎么打包

正文只写本项目最终落地的规则；所有讨论过、评估过、最后否掉的备选方案，统一收进附录，逐条写明与最终方案的差异、适用场景、局限性和取舍原因。

框架 MellowUI（MelUi） 构建 Rollup · UMD · 无 Babel 兼容 IE9+ · 纯 ES5 语法 产物 melui.js + melui-util.js
01

定位与三条原则

先把最容易搅在一起的两件事分开：core 是 UI 底层运行时，util 是纯数据工具。边界不看"谁依赖谁"，而看"会不会产生 DOM、依赖界面样式"。

melui.Core

UI 内核

loading 转圈、遮罩、全局提示、滚动穿透、全局实例管理、zIndex 分配。会创建 DOM，依赖 melui.css。

melui.util

工具库

类型判断、对象合并、防抖节流、日期、金额、URL、文件。纯函数、无副作用、不碰 DOM，可脱离框架单独用。

MelUi.*

组件类

Table / Dialog / Drawer。大驼峰命名空间下的构造类，用 new 实例化，源码内部依赖 core 与 util/base 基础工具。

三条原则：① 源码内部分层，对外接口扁平；② 分层只服务框架维护，不强迫业务写 .Core；③ 代码只写一份，产物按需分开。

本项目有一条额外的硬约束：源码必须能在 IE9 直接跑。构建链路里没有 Babel，Rollup 只做模块合并、不做语法降级。所以源码里不能出现 const / let / 箭头函数 / 模板串 / 对象展开，全部写 var + function。这条约束直接决定了第 5 节的导出写法和附录 A1 的选择。

02

分层与依赖关系

对外只有一个根：全局单例 melui，高频 UI 方法直接挂顶层，完整内核留在 melui.Core 作高级后门；组件用大驼峰 MelUi.*。

03

源码目录结构

原则：一个文件一类职责。loading 的全部逻辑（转圈、遮罩、计数、锁滚动）都在 loading.js；index.js 只做胶水，不写实现。后续要加全局 message、confirm，再新建文件挂进 index。

src/
├─ index.js                主入口：import 组件触发自注册 + 装配 core/util
├─ core/                   UI 内核
│  ├─ index.js             聚合胶水层：import 各模块 + 定义 publicApi
│  ├─ loading.js           showLoading / closeLoading / createSpinner
│  ├─ core.css             Spinner 与 Loading 样式（含 IE9 降级）
│  ├─ message.js           预留：全局轻提示
│  ├─ confirm.js           预留：全局确认框
│  └─ internal/            私有层：只允许 core 目录内部 import
│     ├─ dom.js            createEl / setTransform / textContent 回退
│     └─ zindex.js         zIndex 自增分配
├─ components/             业务组件：每个文件末尾自己注册到 window.MelUi
│  ├─ layout/              布局（只有 css）
│  ├─ button/              按钮样式（只有 css）
│  ├─ dialog/              Dialog / alert / confirm / prompt / Toast
│  ├─ datePicker/          日期选择
│  ├─ drawer/              抽屉
│  ├─ pagination/          分页
│  └─ table/               多文件：先 Core/Renderer/DataStore，build-entry.js 挂 Table
└─ util/                   纯工具，禁止碰 DOM、禁止依赖 core
   ├─ base/                 共享基础层：core / components / util 都可 import
   │  ├─ type.js           isPlainObject / isArray / isFunction
   │  ├─ object.js         mergeObj / 浅拷贝
   │  └─ index.js          聚合导出，供主包 import
   ├─ date.js              日期格式化、时间加减
   ├─ money.js             金额千分位、保留小数
   ├─ string.js            脱敏、uuid、字符串处理
   ├─ url.js               参数解析、query 拼接
   ├─ file.js              blob、下载、base64
   └─ index.js             工具扩展包入口，产出 melui-util.js

internal 与 base 的区别，只看一件事：能不能被别的模块 import。
core/internal/ —— 私有层。只允许 src/core/ 目录内部的文件引用；components、util、业务代码一律禁止。这是可见性约束，里面的函数随时可以改名重构，不构成对外契约。
util/base/ —— 共享基础层。core、components、util 其它模块都可以 import；它随主包打包，业务最终通过 melui.util.xxx 调用，不直接引用源码。
所以两个目录不再共用 internal 这个词：internal 只表示私有，可共享的底层函数统一叫 base。看到目录名就能判断"我能不能引它"，不用翻文档。

为什么拆文件，而不是一个大 js

  • 单个 js 塞几百上千行，后续加 message、confirm 会膨胀成灾难。
  • 拆文件后 git 改动范围小，冲突少；改 loading 动画不碰 mask 代码。
  • 私有实现统一放 internal/，共享的基础函数放 base/，看到目录名就知道谁能引用谁。
04

依赖硬约束

这套目录能长期不烂，靠的是单向依赖。违反任何一条，后面必然出现循环引用或产物污染。

模块允许依赖禁止依赖说明
corecore/internal
util/base 的具体文件		components
util 业务工具		可 取基础工具；不可 把业务工具拖进主包
componentsmelui.Core
util/base		core/internal组件只调公开 UI 能力与基础工具
util/*仅原生 JScore、components、DOM纯函数，保证可独立复用
core/internal无被 core 之外任何模块 import私有实现，改名不算破坏性变更

最容易犯的错：core 为了省事写 import '../util/index.js'（引工具包入口），打包时会把 date、file 全部拖进主包，拆包等于白做。core 只能引 util/base/xxx.js 的具体文件。

05

导出设计

核心是 publicApi 白名单：只有登记过的 API 才会提升到顶层，私有方法留在 Core 里。

最终方案：白名单 + ES5 循环
好处：① 业务只记一个扁平调用 melui.showLoading()，不用写 .Core；② 私有方法留在内核，不会被顺手暴露；③ 新增能力只改 core 两处，主入口一行不动；④ 全程 var + for in，IE9 直接跑。

备选方案：挂载写法见 附录 A1；主入口装配写法见 附录 A7。

先认清一件事：melui 和 MelUi 是同一个对象

组件在自己的 js 末尾就把自己挂上去了（window.MelUi = window.MelUi || {}，然后 MelUi.Dialog = Dialog），最后再写一句 window.melui = window.MelUi。所以小写只是别名，不是第二个对象。

名字是什么怎么用
melui小写别名，指向同一个对象melui.showLoading()
melui.util.mergeObj()
melui.Core.createEl()
MelUi对象本体，组件都挂在这new MelUi.Table(opts)
MelUi.Dialog(opts)

约定：调方法用小写，new 组件用大驼峰。因为同一个对象，写 MelUi.showLoading() 也能跑，但文档统一按小写示范。

src/index.js：你现在的主入口

// src/index.js —— 只做 import：css 触发样式打包，js 触发组件自注册
import './components/layout/index.css';   // 基础样式先引，保证 melui.css 输出顺序
import './components/button/index.css';

import './components/layout/index.js';
import './components/dialog/index.js';
import './components/dialog/index.css';
// datePicker、drawer、pagination 等其余组件同理，一个组件 js + css 两行，此处从略

import './components/table/build-entry.js';   // table 是多文件，入口叫 build-entry
import './components/table/index.css';

export default window.MelUi;

写到 export default 这一行，入口就结束了。里面看不到任何 window.MelUi.Table = Table，因为组件自己挂好了，入口再挂一遍就是重复。

接上 core 与 util 之后，补这一段

// 位置放在 export 之前
import Core, { publicApi } from './core/index.js';
import * as UtilBase from './util/base/index.js';

// 复用组件已经建好的对象，不要新建
var MelUiNS = window.MelUi || (window.MelUi = {});
var key;

// 完整内核留在 Core，作为底层高级入口
MelUiNS.Core = Core;

// 白名单里的高频 API 扁平到顶层，melui.showLoading() 不用写 .Core
for (key in publicApi) {
  if (Object.prototype.hasOwnProperty.call(publicApi, key)) {
    MelUiNS[key] = publicApi[key];
  }
}

// 主包内置基础工具
MelUiNS.util = UtilBase;

// 小写只是别名，指向同一个对象
window.melui = MelUiNS;

export default window.MelUi;

两个容易踩的点：① core.css 的 import 要放回文件最上面，紧跟 layout/button 那两行之后，不要跟这段一起放在末尾，否则转圈样式会被后引的组件样式盖住；② 必须复用 window.MelUi，新建一个小写对象会把组件注册的东西丢掉。

为什么组件自己写 window：为了示例页面能单独跑。
示例页只引一个 components/dialog/index.js 就能演示，不必引 src/index.js。代价是组件不 import core/util/base，extend、resolveEl、addClass 这类小工具各自带一份——这份重复是刻意保留的，不是漏改。入口因此只负责引入，不再重复挂载。

core/index.js：胶水文件，只做 import 与组装

这一段是全文最容易被误读的地方：publicApi 里的函数不是在这里写的，必须先 import 进来。这个文件不写任何实现代码。

// src/core/index.js —— 只做导入、组装、导出
import { showLoading, closeLoading } from './loading.js';
import { createEl } from './internal/dom.js';

// 唯一白名单：登记要提升到 melui.xxx 顶层的 API
// 这里只填真的在 loading.js 里写过的函数，没有实现的不要写进来
export var publicApi = {
  showLoading: showLoading,
  closeLoading: closeLoading
};

// 完整内核：公开 API + 私有底层方法，挂到 melui.Core
var Core = {
  showLoading: showLoading,
  closeLoading: closeLoading,
  createEl: createEl
};

export default Core;

新增一个全局 UI 能力，只在这个文件顶部加一行 import、再往 publicApi 和 Core 各补一行，其余文件完全不动。

core/loading.js：转圈特效与全局 loading

一个文件装完整逻辑：转圈 DOM、遮罩、计数、锁滚动。对外只出口三个函数。

// src/core/loading.js
import { mergeObj } from '../util/base/object.js';
import { createEl } from './internal/dom.js';   // 私有建 DOM 工具

export function showLoading(options) {
  // 完整实现：建 DOM、计数、锁滚动
}
export function closeLoading() {
  // 计数递减，归零才销毁
}
export function createSpinner(container, options) {
  // 纯转圈渲染，内部用 createEl 建节点
}

util/base：单文件单职责，一个文件一类工具

基础层里的文件是共享的，core 和 components 都能 import；每个文件只放一类函数，不要把全部工具堆进一个 js。

// src/util/base/object.js
import { isPlainObject, isArray } from './type.js';

export function mergeObj() { /* 深合并，不污染入参 */ }
export function shallowCopy(val) { /* 浅拷贝 */ }
// src/util/base/index.js —— 基础层出口，供 core 与 components 共用
export { isPlainObject, isArray, isFunction } from './type.js';
export { mergeObj, shallowCopy } from './object.js';

util/index.js：工具扩展包入口，产出 melui-util.js

扩展包与主包是两套产物，加载时向已有的 melui.util 追加，不能整个覆盖，否则主包内置的 mergeObj 会消失。

// src/util/index.js
import * as type from './base/type.js';
import * as object from './base/object.js';
// date.js、money.js、string.js、url.js、file.js 同理，一个文件一行，此处从略

var utilAll = {};
var key;
var group;
var groups = [type, object];   // 其余模块同理往数组里加
var i;

// ES5 合并：IE9 没有 Object.assign
for (i = 0; i < groups.length; i++) {
  group = groups[i];
  for (key in group) {
    if (Object.prototype.hasOwnProperty.call(group, key)) {
      utilAll[key] = group[key];
    }
  }
}

// 追加到已有 melui.util，不覆盖主包内置工具
if (typeof window !== 'undefined') {
  window.melui = window.melui || {};
  window.melui.util = window.melui.util || {};
  for (key in utilAll) {
    if (Object.prototype.hasOwnProperty.call(utilAll, key)) {
      window.melui.util[key] = utilAll[key];
    }
  }
}

export default utilAll;

为什么用循环而不是 ...publicApi：Rollup 只合并模块，不会把对象展开降级成 ES5。一旦写了 ...，IE9 打开就报语法错误。同理 const、箭头函数也不能出现在源码里。

挂载的是函数引用，不是复制。Core 内部改了实现，顶层的 melui.showLoading 自动同步，不存在两份逻辑。

06

打包与产物

两个独立入口，两套产物。主包负责 UI 与组件，扩展包负责完整工具能力，互不牵连。

产物内容说明
melui.js
melui.min.js		core 内核 + 全部组件 + util/base 全部主包。melui.util 要完整可用，所以整个 base 进包；date/money/file 不进包
melui.css
melui.min.css		框架样式（core.css + 各组件样式）core 的 loading、遮罩依赖它，不能脱离
melui-util.js
melui-util.min.js		util/base 全部 + date / money / string / url / file可选扩展包。可单独用于非 MelUI 项目；加载后向 melui.util 追加方法

rollup 双入口配置（示意）

// rollup.config.js —— 两个入口，两套产物
export default [
  {
    // 主包：core + 组件 + util/base
    input: 'src/index.js',
    output: [
      { file: 'dist/melui.js',     format: 'umd', name: 'MelUi' },
      { file: 'dist/melui.min.js', format: 'umd', name: 'MelUi', plugins: [terser()] }
    ],
    plugins: [ postcss({ extract: 'dist/melui.css' }) ]   // 组件 css 合并抽成一个文件
  },
  {
    // 工具扩展包
    input: 'src/util/index.js',
    output: [
      { file: 'dist/melui-util.js',     format: 'umd', name: 'meluiUtil' },
      { file: 'dist/melui-util.min.js', format: 'umd', name: 'meluiUtil', plugins: [terser()] }
    ]
  }
];

全局名必须是 MelUi：主入口最后是 export default window.MelUi，UMD 用这个名字才接得上。小写 melui 不靠 UMD 生成，由源码里那行 window.melui = MelUiNS 挂出去。

构建链路的两个事实

  • Rollup 只负责模块合并与 UMD 包装，不转译语法。源码写什么语法，产物里就是什么语法。
  • 没有 Babel，就没有降级能力。所以"用现代语法写、构建时自动兼容 IE9"这条路在本项目不成立，必须在写代码时就用 ES5。

由此推导出的三条编码铁律：① 只用 var；② 不用箭头函数与模板字符串；③ 不用对象展开与 Object.assign。这三条一旦破防，产物在 IE9 里直接白屏。

07

使用方式

只引主包：只需要 UI 能力

<link rel="stylesheet" href="melui.css">
<script src="melui.js"></script>

<script>
  melui.showLoading();          // 顶层扁平，不用写 .Core
  melui.closeLoading();

  var opts = melui.util.mergeObj({ a: 1 }, { b: 2 });

  var spinner = melui.createSpinner(document.getElementById('box'), {
    size: 24,
    color: '#1677ff'
  });

  var table = new MelUi.Table('#demo', {});   // 组件用 new
</script>

主包 + 工具扩展包：需要日期、金额等

<link rel="stylesheet" href="melui.css">
<script src="melui.js"></script>
<script src="melui-util.js"></script>

<script>
  melui.showLoading();

  // 扩展包加载后，这些方法自动出现在 melui.util 上
  var d = melui.util.formatDate(new Date(), 'yyyy-MM-dd');
  var p = melui.util.formatMoney(1234.56);
</script>

引入顺序：css → melui.js → melui-util.js。扩展包内部用 ES5 的 for in 追加到 melui.util（IE9 没有 Object.assign），只补不覆盖，主包已有的基础工具不受影响。

08

对外暴露规则

大厂通行做法可以概括成一句：源码内部分 core，业务侧看不到 core。Element Plus、Ant Design、axios 都是把内核高频能力代理到顶层命名空间，内核对象只留给深度定制。

入口调用示例放什么业务常用
melui 顶层
（= MelUi，同一对象）		melui.showLoading()
melui.closeLoading()		publicApi 白名单里的高频 UI 方法是
melui.utilmelui.util.mergeObj()全部纯工具函数，自成一组是
melui.Coremelui.Core.internalXxx()完整内核：公开 + 私有底层否，深度定制
MelUi.*new MelUi.Table()组件构造类是

工具不全部扁平到 melui 根上：工具会持续增加，堆在根上迟早和 UI 方法撞名。比如以后 core 加 melui.download()、util 也加 download，就是静默覆盖。放在 .util 下天然分组，文档也好归类。

09

维护流程

新增一个全局 UI 能力（如 message）

  1. 新建 src/core/message.js，写完整实现并 export。
  2. src/core/index.js 顶部 import 这些函数（不做实现，只引入）。
  3. 在 publicApi 与 Core 各登记一行，决定是否提到 melui 顶层。
  4. 打包后即可 melui.message()；不登记的只留在 melui.Core。

新增一个工具函数

  1. 组件或内核会用的基础工具 → 放 util/base/，自动进主包，代码只有一份。
  2. 业务侧才用的格式化、下载类工具 → 新建 util/xxx.js，在 util/index.js 汇总，随扩展包输出。
  3. 不再需要的旧函数在重构期直接删，不做兼容层。
10

命名规范与风险清单

命名约定

  • 函数：小驼峰，动词开头 —— showLoading、closeLoading、mergeObj、formatDate。
  • 全局单例：小写 melui，对应 axios、dayjs 这类单例对象。
  • 组件构造类：大驼峰 MelUi.Table，用 new。
  • 命名空间：工具用 melui.util；内核用 melui.Core，大写 C 作为底层标记。
  • 私有函数：internalXxx 前缀，只出现在 core/internal/。
  • 目录命名：私有实现用 internal，可共享的底层函数用 base；禁止两个目录都叫 internal。
  • 白名单变量统一叫 publicApi。

风险清单

  • ✕ Object.assign(melui, Core)：私有方法全泄露，后续改名即破坏性变更。
  • ✕ 源码写 ...publicApi / const / 箭头函数：Rollup 不降级，IE9 语法报错。
  • ✕ core 引 util/index.js：整包工具打进主包，拆包失效。
  • ✕ 组件 import core/internal/：私有实现一旦重构，组件跟着崩。
  • ✕ melui-util.js 直接 melui.util = utilAll：覆盖主包基础工具，mergeObj 直接消失。
  • ✕ 同一个工具在 core 与 util 各写一份：改 bug 要改两处，迟早不一致。

备选方案：Core 公开 API 的其他挂载写法

最终方案的代码在正文 第 5 节。这里只列与它不同的两种写法，以及各自为什么没被采用。

方式 1：白名单 + 循环挂载（最终方案，已采用）

代码见 第 5 节 · 导出设计。特征：publicApi 放在 core 内部，主入口用 ES5 的 for in 遍历挂载。新增 API 只改 core，主入口不动。这是下面两条的对照基准。

方式 2：白名单 + 对象展开

白名单来源和最终方案一样，差别只在挂载动作：用对象展开代替循环，主入口不再有遍历。

// src/index.js
import Core, { publicApi } from './core/index.js';

const melui = {
  Core: Core,
  ...publicApi      // 这一行替代了最终方案里的 for in 循环
};
  • 优点：主入口最简洁，没有循环样板。
  • 局限：... 是 ES2018 语法。Rollup 只合并模块、不转译语法，产物里仍是 ...，IE9 打开即语法报错。要用这条，构建链必须先补 Babel。
  • 适用：已接转译器的项目，或只面向现代浏览器。

方式 3：手写逐条赋值

// src/index.js
import Core from './core/index.js';

melui.showLoading = Core.showLoading;
melui.closeLoading = Core.closeLoading;
  • 优点：最直白，任何浏览器都能跑，没有额外依赖。
  • 局限：没有白名单清单可查；新增 API 要同时改 core 和主入口两处，容易漏；API 一多样板代码迅速膨胀。
  • 适用：顶层 API 只有 2—4 个的极小库。

禁止写法：整体合并

// 千万不要这么写
melui.Core = Core;
Object.assign(melui, Core);

没有白名单，整个内核一次性摊到顶层：私有方法全部泄露，后续内部改名就是对外破坏性变更；而且 Object.assign 在 IE9 也不存在。

util 工具挂哪：全部扁平 / 收进 .util / 部分提顶层

方案 A：全部扁平到 melui 根

melui.formatDate();
melui.mergeObj();
melui.isObject();
  • 优点：调用最短，和 melui.showLoading() 风格一致。
  • 局限：工具会持续增加，顶层属性越堆越多；一旦与 core 新增方法重名（比如 core 加 download、util 也有 download）就是静默覆盖，排查成本极高；文档分不清 UI 能力与纯数据工具。
  • 适用：工具总数很少（5—8 个），且确定以后基本不再新增。

方案 B：收进 melui.util 子命名空间（本项目采用）

melui.showLoading();      // UI 能力，顶层扁平
melui.util.formatDate();  // 纯工具，收进子命名空间
melui.util.mergeObj();
  • 优点：UI 与工具天然分组；新增工具不会污染顶层，也不可能和 UI 方法撞名；文档归类清晰。lodash 用 _.xxx、antd 用 antd.utils 都是这个思路。
  • 局限：每次调用多写一层 .util。
  • 适用：工具数量较多、还会持续新增（本项目现状）。

方案 C：折中，极少数高频工具额外提顶层（暂不启用）

// 白名单：只提升业务调用最频繁的几个
var utilTopApis = ['mergeObj', 'isObject'];
var i, key;
for (i = 0; i < utilTopApis.length; i++) {
  key = utilTopApis[i];
  melui[key] = UtilBase[key];
}

// 两种写法都可用
melui.mergeObj();       // 简写
melui.util.mergeObj();  // 完整路径
  • 优点：高频工具写起来短，完整路径依然保留。
  • 局限：提一个就多一条同义路径，提多了等于回到方案 A 的命名污染；文档要写两遍。
  • 适用：个别工具调用量极大、团队明确要求少写一层时，按白名单少量开放。

对外入口形态：扁平 + Core 后门 / 全扁平 / 全大驼峰

方案 A：业务用扁平 API，melui.Core 只作高级后门（本项目采用）

melui.showLoading();              // 业务日常
melui.closeLoading();
melui.util.mergeObj();
var table = new MelUi.Table('#dom', {});

melui.Core.createEl();    // 深度定制才用，文档放高级章节
  • 优点：业务代码简洁；源码内部仍保留 core 分层，维护不乱；高级能力留了入口。
  • 局限：melui.Core 下的内部方法不承诺向后兼容，业务不应依赖。
  • 适用：绝大多数 UI 框架（Element Plus、Ant Design、axios、layui 都是这套）。

方案 B：全部放 melui，彻底删掉 melui.Core

  • 优点：只有一个命名空间，最简。
  • 局限：底层内核接口无处安放，要么全公开（等于把私有方法送出去），要么以后再加 .Core，属于破坏性变更。
  • 适用：内核极薄、确定永远不会对外暴露底层能力的库。

方案 C：全部大驼峰 MelUi.showLoading()

MelUi.showLoading();
var ins = new MelUi.Table('#dom', {});
  • 优点：全局只有一个名字，写法统一。
  • 局限：JS 社区里大驼峰代表构造类，方法与类混在同一下面会产生误读，new MelUi.showLoading() 这类误用迟早出现。
  • 适用：部分国内传统 UI 库的历史写法，不建议新框架采用。

大厂为什么要分这一层：core 是源码内部的维护分层，不是给业务用的命名空间。业务看到的是扁平 API，框架维护者看到的是 core 目录，两件事分开，代码才好改。

附录 · A5

胶水文件与简写片段：最容易看晕的一处

讨论过程中经常出现这样的片段：直接写一个白名单对象，成员是 showLoading、closeLoading，没有任何 import 语句。这种片段在原理讲解里成立，但照抄进项目就会出问题。

为什么会让人一头雾水

因为片段把 import 省掉了，读者会以为函数是在 core/index.js 里现写的，甚至以为要在这个文件里写 function showLoading(){} 的实现。这正好违反了第 3、5 节定下的规则：index.js 是胶水层，不写实现。

正确顺序只有三步：① 从 loading.js、internal/*.js 把函数 import 进来；② 把导入的函数填进 publicApi（以及 Core）；③ 导出。任何一步颠倒，都会变成"在入口文件里造函数"。

看到简写片段时怎么判断

  • 片段里出现函数名，但上方没有 import、下方没有 function 定义 → 这是省略了导入的示意片段，不能直接用。
  • 片段里出现 export default { ...publicApi } 这类写法 → 这是未接 Babel 时不可用 的语法，本项目禁止。
  • 白名单统一叫 publicApi。

一句话判断法：入口文件里只应该出现 import、对象字面量、for 循环、export。出现大段 DOM 操作或业务逻辑，就是写错文件了。

主入口两种装配写法：一个对象 / 两个对象

两种写法都能让 melui.showLoading() 跑起来，差别只有一件事：melui 是不是第二个对象。

写法 A：复用 MelUi，melui 只做别名（采用）

代码见 第 5 节。特征：不新建对象，拿组件已经建好的 window.MelUi 往上挂 core 与 util，最后把 window.melui 指过去。

  • 优点：组件注册的 Dialog、Toast、Table 一个都不会丢；示例页单独引组件也能跑；全局只有一份对象，不存在两套状态。
  • 局限：类和方法混在一个对象上，只能靠命名约定区分（大驼峰是类）。

写法 B：新建独立的小写对象（旧稿写法）

// src/index.js —— 新建一个小写对象，只装方法
import Core, { publicApi } from './core/index.js';
import * as UtilBase from './util/base/index.js';

var melui = {};
var key;

melui.Core = Core;

for (key in publicApi) {
  if (Object.prototype.hasOwnProperty.call(publicApi, key)) {
    melui[key] = publicApi[key];
  }
}

melui.util = UtilBase;

if (typeof window !== 'undefined') {
  window.MelUi = window.MelUi || {};
  window.melui = melui;
}

export default melui;
  • 优点：大小写职责彻底分开，小写只装方法，大写只装组件，一眼能分清。
  • 局限：组件末尾写着 window.melui = window.MelUi，会把别名指回大写对象；入口新建的那个对象随即没人引用，melui.showLoading 变成 undefined。要采用这条，必须把所有组件里那行删掉。
  • 适用：组件不自己注册、全部由入口集中挂载的项目。
写法对象数与组件的关系要改组件取舍
A 别名1复用，组件先注册、入口后装配不用改✅ 采用
B 独立对象2并行，各自一份要删掉组件的别名行❌ 不采用
