------------------------------------------ ## 两种主流打包策略 ------------------------------------------ ### 策略 A：分开打包（推荐，大厂常用，适合你） 1. Rollup 打包**库代码（src/**） → 输出到 `dist/` 根，js/css，这是**给业务开发者使用**的 2. 单独打包 / 复制**示例页面 examples/** → 输出到 `dist/demo/`，仅预览，业务项目**不会引入这里的 js** > > 源码侧，示例 html 不要写在 src 下面，单独新建 `examples/` 文件夹，和 src 同级。 ``` 源码根目录 ├─ src/ # 源码（core/components/util/styles） ├─ examples/ # 所有demo页面，写在这里，和src平级 │ ├─ loading.html │ ├─ spinner.html │ ├─ button.html │ ├─ table.html │ └─ grid.html ├─ rollup.config.js └─ package.json ``` ------------------------------------------ 具体怎么打包Html示例文件的 ### 策略 A 里面，一般大厂本地测试时肯定是组件一个个引入，比如我们的table引用很多个js，但是打包后的示例肯定只引入一个table.js table.css或 melui.js, melui.css，它们打包时这些示例文件难道要一个个修改？还是说本地测试时就引入打包后的文件进行测试的 ------------------------------------------ # 核心一句话 **两套环境，两套引用写法，不是手动一个个改html！靠脚本自动替换路径。** > > 本地开发（examples/*.html）：直接引入 src 源码，分组件逐个加载，改代码浏览器立刻刷新调试。 > 打包发布（dist/demo/*.html）：脚本批量替换html里面script/link路径，统一改成引用 `../melui.min.js` / `../melui.min.css`。 大厂不会人工逐个修改demo页面，人工改会漏、容易出错。 ## 1. 本地开发阶段（examples目录，写组件、调试） examples下面每一个demo html，**直接引用src源码**，拆分引入各个组件js/css。 examples/table.html： ``` ``` ✅ 好处： 1. 改src下面任意js/css，刷新页面立刻看到效果，**不需要每次都执行rollup打包**，开发效率极高 2. 调试可以直接断点进table、spinner源码，看原始代码，不是压缩后的产物 3. 开发阶段哪里报错，直接定位到对应组件源码 > > 这就是你说的：本地测试组件一个个引入。 ## 2. 打包构建阶段（npm run build） 打包脚本做两件独立任务： 1.
