                一、真实业务场景的表格功能需求分析
------------------------------------------------------------------------------------------


你总结的这几条，基本是**录入型表格**的核心骨架。但真实业务跑下来，还有一些你没提到但几乎一定会遇到的需求，以及一些看起来 "应该有" 但其实不该表格控件管的东西。我按优先级分层说。

---

## 一、你已经提到的 —— 核心刚需，没毛病

表格

| 功能 | 必要性 | 说明 |
| --- | --- | --- |
| 表头固定 | 必须 | 数据行多了不固定表头根本没法看 |
| 左侧 N 列冻结 | 必须 | 行号、名称、ID 这些列滚走了就不知道自己在看哪行 |
| 列类型自定义（input/readonly/radio/checkbox/ 下拉） | 必须 | 这是表格的灵魂，不同列不同输入方式 |
| 合计行 / 小计行 | 高频 | 金额、数量类的表格几乎都要 |
| 行状态标记（新增 / 修改 / 已保存） | 高频 | 保存时只提交改过的行，这个很实用 |
| 增删行 | 必须 | 录入型表格基本操作 |
| 读取全部数据 | 必须 | 保存按钮的基础 |

这 7 条是底座，没这些根本不能用。

## 二、你没提到但真实业务几乎一定会有的需求

### P0 —— 大概率要做

**1. 列宽拖拽调整**
你现有控件是写死 width 的，但业务用久了一定会有人提："这列太窄了能不能拉宽一点"。用户对列宽的控制欲很强。这个功能不复杂，但要和固定列、表头对齐协同好。

**2. 单元格校验**
你已经有`must`（必填）和`unique`（唯一），但真实业务还会遇到：

- 数字范围校验（金额不能为负、面积不能超过 9999）
- 格式校验（手机号、身份证、日期格式）
- 联动校验（A 列填了，B 列必填）
- 校验不通过时标红 + 提示文字

这个不是表格控件自己写死的，而是要提供一个`validator`配置点，让业务方传校验函数。

**3. 行选中 + 批量操作**
你 Demo 里已经有 checkbox 列了。批量删除、批量保存、批量导出 —— 这是后台管理系统的标配。

**4. 分页**
你现有控件已经有了。录入型表格一般每页 20-50 行，不会真的一次渲染几百行。分页比虚拟滚动实用得多。

**5. 表头排序**
点列头排序。你现有也有了。报表型表格必做，录入型表格看业务。

**6. 行号自动编号**
你现有有`isSerialCol`。这个看着不起眼，但业务方一定会要 ——"这是第几行"。

### P1 —— 很常见，看业务复杂度

**7. 列显示 / 隐藏**
列多了（15 列以上），用户会希望 "我只看这几列，其他先收起来"。这个功能可以做成右上角齿轮图标，勾选显示哪些列。

**8. 隔行变色 + hover 高亮**
你现有已经有了。这个是体验细节，但少了会觉得糙。

**9. 单元格合并（横向表头合并）**
你现有有`merge`参数。真实业务里，一级表头分组很常见 —— 比如 "基本信息" 下面分 3 列，"交易信息" 下面分 4 列。

**10. 单元格内联动按钮**
你现有有`component`/`component2`参数（输入框旁边加个 "查询" 按钮）。这个很实用，比如选楼盘 —— 输入框旁边一个按钮，点开弹窗选数据。

**11. 导出 Excel**
你现有有。后台系统标配。

**12. 数据回填时的 "只读锁定"**
保存过的行，某些列变成只读（比如面积保存后就不能改了）。你现有有`setSomeColumnReadonly`，这个要保留。

### P2 —— 看业务，不是每个项目都要

**13. Excel 式复制粘贴**
用户从 Excel 复制一段数据，直接 Ctrl+V 粘贴到表格里，自动按行列填入。这个在录入密集型业务里非常香，但实现成本不低。

**14. 行拖拽排序**
用户用鼠标拖行调整顺序。一般用于排序类业务（比如菜单排序、商品排序）。

**15. 列拖拽换顺序**
用户拖动表头列调整列的显示顺序。比列显示 / 隐藏更高级一点。

**16. 分组小计行**
不是简单的最后一行合计，而是按某个字段分组，每组末尾插一个小计行。你现有有`list-summary`，这个方向是对的。

**17. 树形表格（父子行）**
比如订单列表 —— 一个主订单下面展开 N 个子订单。这个复杂度跳升一个量级，一般业务不需要。

**18. 打印**
直接打印表格内容。一般业务用浏览器打印就行，不需要专门做。

## 三、看起来 "应该有" 但其实不该表格控件管的

这些需求业务方可能会提，但应该由业务层自己处理，不要塞进表格控件：

表格

| 需求 | 为什么不该表格管 |
| --- | --- |
| 单元格点击弹窗选数据 | 表格只负责触发回调，弹窗用什么组件（Dialog/Dropdown）是业务层的事 |
| 行数据保存到后台 | 表格只负责返回数据，发 AJAX 是业务层的事 |
| 权限控制（某角色不能编辑某列） | 表格只暴露`readonly`配置，权限判断是业务层传进来的 |
| 数据字典转换（1→男，0→女） | 表格只负责显示原始值，转换可以在配置层用`formatter`做，但不要做死 |
| 复杂的跨表联动 | 两个表格之间的数据联动，是业务编排的事 |

## 四、录入型 vs 展示型 —— 你要先想清楚定位

这个很关键，因为两种表格的功能侧重完全不同：

表格

| 维度 | 录入型表格（你现在做的） | 展示型表格（报表列表） |
| --- | --- | --- |
| 核心诉求 | 快速录入、校验、增删行、收集数据 | 快速浏览、筛选、排序、导出 |
| 行数量 | 每页 20-50 行 | 每页 20-100 行，可能更多 |
| 单元格类型 | input/textarea/radio/button 等可编辑 | 纯文本为主 |
| 虚拟滚动 | 不太需要（行少） | 行多了才有价值 |
| 行状态标记 | 必须（新增 / 修改 / 已保存） | 不需要 |
| 合计行 | 高频 | 高频 |
| 分页 | 必须 | 必须 |
| 列拖拽排序 | 少用 | 常用 |
| 列显示隐藏 | 少用 | 常用 |

从你的 Demo（房产评估明细录入）和现有控件功能来看，你做的是**录入型表格**。这个定位下：

- **虚拟滚动不用做**—— 每页就 30 行，没必要
- **列拖拽换顺序不用做**—— 录入表格列顺序是固定的业务逻辑
- **列显示 / 隐藏可以缓一缓**—— 录入表格列少则几列多则十几列，一般都要看全
- **重点要做好的是：单元格编辑体验、行状态追踪、数据校验、增删行的性能**

## 五、我的判断：你总结的方向基本对，但有几个容易漏的

你列的 7 条是骨架，真正做起来还会加这些：

1. **列宽拖拽** —— 一定会有人提
2. **单元格校验机制** —— 不是写死校验规则，而是提供一个可配置的校验钩子
3. **行选中批量操作** —— 你已经有了
4. **分页** —— 你已经有了
5. **列显示 / 隐藏** —— 列数超过 15 列就会有人要
6. **单元格旁边的组合控件**（输入框 + 查询按钮）—— 你现有有，很实用

其他的（复制粘贴、行拖拽、树形表格）—— 遇到再说，不要提前做。

## 六、重构时的建议

不要追求大而全。你现有控件已经跑了 5 年了（2020 年到现在），功能是慢慢加上去的，不是一开始就设计全的。

新控件建议：

- **第一版只做你列的 7 条 + 列宽拖拽 + 校验钩子**
- **其他功能（排序、分页、合计行、导出）作为第二阶段迭代**
- **不要一开始就做虚拟滚动、列拖拽、树形表格**—— 这些是复杂度黑洞，而且你的业务场景大概率用不上

你现有控件最大的问题不是功能少，是性能差。重构的核心目标应该是：**同样的功能，渲染快 3 倍，操作不卡**。而不是趁重构加一堆新功能。

功能可以慢慢加，但架构选错了，后面再加功能会越来越卡。
